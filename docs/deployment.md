# 直接部署与备份恢复

当前主方案为 Node.js + PostgreSQL，不需要 Docker。此文档是部署操作说明；尚未创建生产资源或部署公网服务。

## 运行要求

Node.js 22、PostgreSQL 17、匹配或更新主版本的 pg_dump / pg_restore、HTTPS 反向代理。构建与运行的操作系统和 CPU 架构需兼容，不把 macOS 依赖包直接复制到 Linux。生产主机使用应用专用账号；数据库迁移账号与运行账号分开，运行账号不需要超级用户或建库权限。

## 准备与构建

在部署平台或与服务器兼容的构建环境执行：

```sh
npm ci
npm run typecheck
npm test
npm run build
```

测试只能连接专用开发/测试库，不能在生产数据库上运行。构建产物位于 `.next/standalone/`，构建脚本会复制静态资源并移除该目录中的 `.env*` 副本，源 `.env` 不变。不要把源码目录、开发数据库文件和备份一并公开。

部署复制整个 `.next/standalone/` 目录。每次发布放到独立版本目录，保留上一个产物；不要在服务进程正在使用的目录中重新构建。数据库迁移在源码工作目录单独执行 `npm run db:migrate`，需要完整依赖与内容快照，运行包不承担迁移。迁移前备份；审核结构变化，当前迁移为追加结构和不可覆盖的内容版本。

## 环境与启动

运行环境设置 DATABASE_URL、APP_URL，详见 `.env.example`。应用地址为真实 HTTPS 域名，不再配置认证密钥或邮件服务。密钥通过进程环境或主机密钥管理提供，不放进部署产物。

本机验证可使用 Node 的 env-file 功能，在项目根目录执行：

```sh
PORT=4100 HOSTNAME=127.0.0.1 APP_URL=http://localhost:4100 node --env-file=.env .next/standalone/server.js
```

生产服务模板位于 `deploy/life-in-order.service`，需按真实路径、用户和 Node 位置调整；模板凭据文件 `/etc/life-in-order.env` 应仅允许管理员读取。`deploy/Caddyfile.example` 展示 HTTPS 反向代理，替换域名并确认 DNS 后才启用。两份模板均未在本机安装。

代理只转发可信客户端 IP，覆盖外部伪造的转发头。匿名统计保留同源校验、输入限制与软限量。应用端口仅绑定回环地址，数据库不对公网开放。

## 发布检查

`GET /api/health` 在数据库与当前公开知识可读时返回 200；数据库失败或缺少内容返回 503，不输出凭据。该检查不证明备份可恢复。

发布后检查健康、主题浏览、连续阅读、依据展开、搜索与匿名统计；确认旧认证/计划接口为 410，浏览器无会话请求。

回滚先确认旧应用能读取当前数据库与内容版本；不能只切旧产物就假设兼容。失败时停止切换，保留当前库与备份，不执行重置或覆盖恢复。

## 备份

工具在有 PostgreSQL 客户端的源码运维工作目录执行：

```sh
npm run db:backup -- backups/首次唯一文件名.dump
```

使用自定义格式；文件权限为 0600，拒绝覆盖已有文件，失败不会把不完整文件标为成功备份。不通过命令参数传递密码。备份可能含历史用户个人数据，禁止提交仓库或放入网站静态目录。

本地副本不等于容灾。生产阶段需另行配置加密异地存储、计划调度、失败告警、保留与删除周期。当前不自动清理旧备份，避免误删唯一副本。历史账号数据及备份清除期限需单独确定，当前不自动删除。

## 恢复到独立空库

先由管理员创建独立空数据库。设置 RESTORE_DATABASE_URL，保持 DATABASE_URL 指向源库；不要将凭据直接粘贴到共享终端历史中。

```sh
npm run db:restore -- backups/首次唯一文件名.dump
```

恢复工具拒绝同源库和非空库，使用单事务与 exit-on-error，不使用 clean；不自动切换应用连接，也不自动删除任何数据库。只从可信备份恢复，pg_restore 会执行备份中的数据库定义。备份不含集群角色、授权、外部文件或邮件服务配置，这些需单独管理。需要 SSL 证书时配置 PGSSLROOTCERT 等 PostgreSQL 客户端环境变量。

恢复后核对所有表、知识 772 条、内容版本、用户计划与进度及外键约束，再用应用连接目标库验证。只有检查通过才考虑切换连接，并保留原库。

## 已做演练

`npm run test:recovery` 会创建两个随机命名专用数据库，给源库执行真实迁移并写入虚构计划，备份并恢复到目标，再核对各表数量、完整计划、知识和外键；最后只删除自己创建的测试库和临时文件。需要建库权限，不能将该命令用于生产环境。

本机演练已通过，未覆盖现有开发库。

## 可选 Docker

Docker 不是运行前提。Dockerfile 提供 runtime 和 migration 两个目标；运行镜像使用非 root 用户，不携带本地 .env。构建阶段只有公开的占位认证值，真实运行必须注入配置。镜像不包含数据库服务和自动备份。

CI 容器检查默认不执行，设置仓库变量 CHECK_OPTIONAL_CONTAINER=true 才启用。本机 Docker 守护进程未运行，尚未实测容器构建；直接 Node 运行包单独验证。

## 待用户提供的部署信息

正式部署地区与主机、域名与 DNS 管理方式、数据库服务凭据、运营主体及联系方式、备份保存和删除期限。当前没有替用户购买服务或部署公网应用。

参考：[PostgreSQL pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html)、[pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html)。

## 可选语义检索运行要求

启用智能匹配时，需要 PostgreSQL 安装 pgvector 扩展，并在应用所在主机运行本地 Ollama 嵌入模型。基础关键词方式不要求模型在线。运行时注入 EMBEDDING_URL、EMBEDDING_MODEL 和固定摘要 EMBEDDING_MODEL_DIGEST；这些配置不会打包进独立运行包。迁移、索引、模型升级和隐私边界见 [语义检索说明](semantic-search.md)。备份包含向量和扩展声明，恢复前目标主机需安装兼容的 pgvector 二进制；也可重建派生索引。公开上线前仍需验证模型并发、超时和资源容量。

## 后台使用统计（2026-11-10）

基础迁移创建 usage_events。执行 `npm run usage:report -- 7` 查看汇总；生产应每日调度 `npm run usage:prune`，该命令清理三十天前事件。新写入与报告也清理，停服时不自动执行；本轮未安装系统计划任务。备份含统计表，备份副本由既有备份策略清理。统计接收失败不影响内容服务健康。
