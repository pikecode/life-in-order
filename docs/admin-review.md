# 网页内容管理

管理入口：https://ompeak.com/admin/ 。公开阅读仍免登录。管理页采用独立单账号，不提供公众注册，也不复用已停用的历史账号。

## 登录

账号：`admin`。初始随机密码在维护者本机 `output/private/admin-access.txt`，服务器交付副本为 `/root/life-in-order-admin-access.txt`。文件权限 0600，目录不进入 Git；请私下保存，可交由密码管理器保管。

密码以 scrypt 摘要保存在 `/etc/life-in-order-admin.json`，通过 systemd LoadCredential 仅交给管理进程。公开阅读进程不加载此文件或数据库维护凭据。会话 Cookie 为 HttpOnly、Secure、SameSite=Strict，最长 8 小时，退出即失效；管理服务重启也会使全部会话失效。

## 日常操作

1. 登录后查看“更新报告”和“最近检查”。每日自动任务也会更新最近检查结果。
2. 点击“检查上游更新”，跳转任务页，执行结果自动刷新。关闭页面不取消任务；网络失败会明确显示未完成，不当作无更新。
3. 有变更时打开报告，从左侧文件目录选择文件，左右查看修改前后完整原文。新增/删除文件也明确标记。
4. 核对来源、时效、地区及许可，勾选确认后“标记已审阅”。记录绑定提交、报告摘要和路径，报告变化后不能沿用旧记录。
5. 点击“准备并校验版本”。这一步只导入待发布内容，不改变读者看到的版本。
6. 全部变更文件已审阅、版本准备完成且报告无阻断项后，进入发布确认页。核对当前/目标提交，填写备注并勾选确认，再执行“备份并发布”。
7. 发布历史可进入回退确认页，同样需要备注与明确确认，执行前自动备份。

管理页与命令行共用原来的维护脚本和完整校验。网页在提交任务及实际执行前都检查审核条件；维护命令之间使用数据库锁，防止定时检查与网页任务同时改写快照。

## 运行与失败处理

- 管理服务：`life-in-order-admin.service`，专用系统用户 `lifeadmin`，仅监听 `127.0.0.1:3101`，由 Nginx `/admin/` 代理。
- 公开应用仍为 `life-in-order.service` / `127.0.0.1:3100`，数据库只读权限不提升。
- 管理进程可写目录仅限源码下 `content/updates` 和 `backups`；定时上游检查改用同一用户，避免报告所有权冲突。
- 后台任务及审阅记录保存在 `content_admin_jobs` / `content_admin_reviews`；最新检查为 `content_admin_checks`。公开数据库运行账号没有这些表的读取或写入权限。
- 任务串行执行；超时会停止本任务的进程组并记录失败。管理服务异常重启会把未完成任务标为中断，需核对当前线上状态后重试，不自动再次发布。
- 登录失败每 IP 最多 5 次/15 分钟，另有全局限制；所有操作检查来源及会话确认令牌。原始 Markdown 以转义文本对照，不执行 HTML 或脚本。

查看状态与日志：

```sh
systemctl status life-in-order-admin
journalctl -u life-in-order-admin -n 80 --no-pager
```

任务检查遇 GitHub 超时时，可在网络恢复后重新点击；不要因此手工删除版本数据。许可、章节或专题结构变更导致阻断时，需要维护者先核实并更新解析规则。

## 凭据生成与重置

新环境创建私有新文件（命令拒绝覆盖已有文件）：

```sh
node --import tsx scripts/admin-password.ts /私有目录/admin.json /私有目录/admin-access.txt admin
```

生产重置时先由管理员私下备份现有配置，生成新配置并替换 systemd LoadCredential 指向的文件，然后重启管理服务；旧会话随重启失效。不要把明文密码、配置或浏览器登录状态提交到 Git。

本地开发需单独设置管理地址，如 `APP_URL=http://127.0.0.1:3101`、`ADMIN_CONFIG_FILE=/私有配置路径`，数据库连接需具备维护权限，再运行 `npm run admin:start`。不要将管理地址或维护连接覆盖到公开阅读进程。

当前没有多管理员、权限分级、密码找回邮件或消息推送。只有真实上游变更才会出现生产审核报告；不向生产库添加演示候选或代替用户审阅内容。
