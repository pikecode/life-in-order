# 退租问题处理台

目标：把租房退租的一件事，从描述 → 用户确认方向/条件 → 挑选事项 → 下一步行动连成闭环。不是通用聊天助手，不推断法律责任或把未知条件当成事实。

方案：独立 `/handle/rental` 样板，复用 rental-v1 已发布任务、来源、适用规则、前置检查、状态及跟进逻辑。相比直接覆盖旧编辑器，隔离新体验更便于评估；相比新增任务引擎和模型代理，复用规则更简单。

设计：
- 问题描述固定保留，可修改；只给交接、押金结算、押金争议三个明确方向，用户点击确认。不宣称自动理解，初版不接大模型拆解。
- 阶段及押金争议条件由用户明确回答，允许不确定。
- 仅使用交接、结算、争议三项已有任务。每项可“适合我”“还不确定”“暂不处理”，暂缓可恢复；不改为自动完成状态。
- 右侧持续展示已选、待确认、暂缓与可以开始的第一件事；手机分步呈现。缺少前置事项时明确提醒，并提供显式加入，不暗中补选。
- 行动支持开始、完成、卡住与跟进记录，完成后提示下一项。完整依据复用阅读面板。

数据与保存：PlanData 增加可选 workspace（场景种类、问题、确认方向、挑选状态和阶段），只允许 rental-v1 的三项任务。原计划没有该字段，保持原样。planData、导出和导入保留；原编辑器遇到这类保存/导入计划转到处理台，首页继续入口也按种类路由。无需新数据库表或任务发布版本。

草稿使用 lio-draft:rental-workspace，按 owner 和计划 ID 隔离，过期会话不能读取其他账号保存的草稿。明确保存才写数据库，复用现有登录、归属检查与 revision 冲突机制，冲突保留本地内容并支持导出；不自动覆盖云端。问题描述不得含身份证、完整地址等隐私，更新使用说明。

实施：先领域 schema 与纯函数测试，再保存/恢复和客户端流程，接首页及真实来源入口，最后验证条件、依赖、暂缓恢复、状态推进、草稿、冲突和跨账号隔离。KISS/DRY 复用规则及接口；单一职责分离选择元数据与任务状态；YAGNI 只做退租样板，不扩到其他三个场景。

完成：领域、页面、首页与来源入口、旧编辑器跳转、导入导出及隐私说明已实现。草稿完整键为 lio-draft:rental-workspace:{anon|user:账号}:{new|计划ID}。31 项测试、类型检查及构建通过，浏览器验证记录见 ../verification.md。无需新依赖或数据库结构迁移。
